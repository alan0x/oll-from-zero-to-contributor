# 《从零理解 OLL：从一句问题到一堂可交互白板课》

这不是一份字段手册，而是一本面向新开发者的工程入门书。

读完后，你应该能够回答下面这些问题：

- OLL 是什么，为什么不能直接让大模型操作 Canvas？
- `learning-coach`、Octos 后端、`octos-web` 和 OLL 仓库各自负责什么？
- 用户说出一个问题后，一堂课如何生成、保存、传输、播放和恢复？
- Authoring Profile、Canonical Profile、Semantic Board State 分别是什么？
- Step、Beat、Action、Node、Fragment、Variable 和 Student Task 如何协作？
- 动画、滑杆、几何拖点、3D、学生笔迹和白板局部增强分别属于哪一层？
- 如何修改一个现有能力，或给 OLL 增加一种新能力？
- 如何测试，如何判断问题发生在哪个仓库，如何提交一个可审核的改动？

## 本书采用的版本前提

本书以“经过代码和自动测试核对的开发版本”为准，不再假定开发分支已经合入 `main`。当前核对日期、精确提交、依赖关系和未合并边界见[版本基线与当前状态](./版本基线与当前状态.md)。

正文中的“已实现”表示在该版本基线中存在代码和测试，不等于已经发布到生产，也不等于四个仓库的 PR 都已合并。开始开发前，应再次核对各仓库当前分支、锁定的 OLL commit 和测试结果。

OLL 目前仍使用 DSL 版本 `0.1`。这表示协议尚未承诺永久稳定；贡献者修改协议时必须同时处理 Schema、语义校验、Normalizer、Reducer、Runtime、Skill 生成和消费方依赖。

## 四个仓库

本书中的“Skill 仓库”专指 `learning-coach`：

| 名称 | 本地目录 | 最简单的职责说明 |
| --- | --- | --- |
| OLL | `<workspace>/octos-lesson-language` | 定义课堂语言，并提供校验、转换和播放 Runtime |
| learning-coach | `<workspace>/learning-coach` | 把用户问题生成成合法 OLL 课件或局部增强结果 |
| Octos | `<workspace>/octos` | 运行 Agent 和 Skill，访问模型，管理会话、文件和 UI 协议 |
| octos-web | `<workspace>/octos-web` | 提供 `/learn` 产品界面，接收课件并播放白板课程 |

`<workspace>` 表示你自己的项目目录。不要把某位开发者的 home、`/private/tmp`、worktree 或一次会话的临时目录写成项目约定。

一句话记忆：

> OLL 规定“课件怎么写”，learning-coach 负责“写课件”，Octos 负责“让 Agent 调用它并交付文件”，octos-web 负责“把课件变成用户看到和操作的课堂”。

## 贯穿全书的例子

用户提出：

> 请结合单位圆和 `y = sin(x)` 的函数图像，解释角度旋转如何变成周期波动。最后出一道让我拖动圆周点找到正弦最大值的小练习。

最终课堂应该包含：

- 一个单位圆；
- 圆周上的点 `P`；
- 点到横轴的投影；
- 一张正弦函数图；
- 一个全课共享的变量 `theta`；
- `theta` 变化时几何图和函数图同步更新；
- 自动动画；
- 学生滑杆和几何拖点；
- 一个可判定完成条件的学生任务。

最后一项只因为用户明确要了“小练习”。如果用户只要求解释和自由拖动，系统可以提供控件，但不能擅自把探索升级成有标准答案的任务。

这个例子足够小，便于看懂；又同时覆盖了 OLL 的核心结构、变量、动画、交互和跨视图联动。

## 本书不做什么

- 不把大模型内部推理当作 OLL 的一部分。
- 不把浏览器 DOM、SVG 或 Canvas 坐标当作 OLL。
- 不把学生笔迹伪装成老师生成的 OLL 节点。
- 不把尚未定义的插件设想写成已经存在的协议。
- 不要求读者先懂项目内部简称。每个术语第一次出现时都会解释。

如果正文与代码冲突，以代码、Schema 和自动测试为准；然后应修正文档，而不是让二者长期不一致。
